# Visual redesign brief

## Visual redesign — explicit Fable 5.1 design authority

This is newly requested planned work, not a completed redesign. Change ID: `visual-redesign`; roadmap S-06. Preserve the shipped accounting, authentication, ownership and persistence behavior.

**Fable 5.1 is the sole designer.** Fable 5.1 must read and apply the `frontend-design` skill (available locally at `/Users/sebastian.f/.codex/skills/frontend-design/SKILL.md`; discover its installed equivalent if running elsewhere). It decides the complete visual direction, information hierarchy, screen layouts, component appearance, typography, colors, spacing, responsive behavior, interactions, transitions and animations. This is an explicit exception to coordination-only orchestration: Fable performs design work and visual acceptance, but delegates application implementation and tests to explicitly selected Opus/Sonnet subagents. It must not spawn Fable subagents or silently substitute a different designer.

Before implementation, Fable must produce a complete design specification with concrete tokens, screen/component specifications and visual references or mockups as useful. Cover login, empty/populated subscription views, balances, participant management, prices/break months, manual payments and standing orders. Specify loading, empty, error, success, focus, hover, disabled and destructive-confirmation states; keyboard behavior, mobile layout and reduced-motion alternatives. Specify motion properties, easing and behavior in implementation terms, without adding project schedule estimates or calendar metadata. No unresolved design choices may be handed to implementers.

Opus/Sonnet implement the approved specification, not their own interpretation of its visual direction. They may resolve mechanical code choices within it. If a design detail is missing, inconsistent or infeasible, checkpoint the issue and return it to Fable 5.1 for a concrete decision; do not improvise appearance, copy hierarchy, interactions or animation. Independent reviewers may challenge the design; Fable resolves the findings and updates the specification before dependent implementation proceeds. Routine design decisions do not require a user interview.

Follow the 10x change flow on this existing app: `10x-new` → `10x-research` → `10x-frame` for the usability/design scope → Fable's `frontend-design` specification → `10x-plan` → independent `10x-plan-review` and resolved findings → `10x-implement` in verified phases → `10x-impl-review` → Fable visual acceptance → `10x-archive`. Read full skill instructions and referenced schemas before applying them. Keep foundation requirements/roadmap/test-plan aligned, active artifacts under `context/changes/visual-redesign/`, and canonical plan Progress. Archive using the project's date-free convention only after completion.

Acceptance: all existing workflows remain usable; relevant regression checks pass; desktop and narrow mobile layouts are inspected in a real browser; keyboard/focus, validation, feedback and reduced motion match the design. Fable compares the actual implementation with the specification and resolves discrepancies. Save real screenshots and review evidence, not only mockups. Deploy the accepted revision through the existing release flow, verify it live and replace certification screenshots with captures of that identifiable release. No upload to 10x without explicit confirmation.

Every subagent checkpoints meaningful progress and unfinished work; the designated status writer reconciles goals, evidence and STATUS. Do not treat previous release acceptance as evidence that this new design has passed.
