# Candidate K1: `routeIndex` as a raw public mutable field (deferred, re-justify - see independent review correction)

**Status after independent plan review**: deferred. The plan review at `reviews/plan-review.md` (verdict: approve with required changes) tested this candidate's top rank with a counter-question and found three of its four supporting claims contradicted by the clone. The corrections are recorded below in place of the original claims, per the review's finding F7; the two axes that survive (bounded, fully-enumerated blast radius; an additive first step, for the test phase only) did not, on their own, outweigh the loss of the other three, so K1 no longer heads the ranking. Full detail: `reviews/plan-review.md`'s F7 entry and counter-question section, and `D-004`'s updated Review objection/Resolution.

## Current shape (evidence, read directly at the pinned commit)

`src/request.ts:53` declares `routeIndex: number = 0` as a plain public field on `HonoRequest`. It is written in exactly one place, `src/compose.ts:44` (`context.req.routeIndex = i`), inside the composed-dispatch loop. It is read by `request.ts` itself at lines 104, 112, 114, 446 (parameter resolution and `routePath()`). Outside `compose.ts`/`request.ts`, it is read or written directly, with no accessor method, in exactly 3 files (`ast-grep run --pattern '$X.routeIndex' --lang ts src`, corroborated with `rg`): `src/middleware/method-not-allowed/index.ts:65`, `src/middleware/combine/index.ts:101,106`, `src/helper/route/index.ts:59,83,108`.

**Correction (independent review, re-verified directly in the clone)**: the field's *declaration* at line 53 carries no JSDoc of its own, but the field itself is documented for user-land reads. `src/request.ts:419` (inside the public `matchedRoutes` getter's `@example` JSDoc block) reads `i === c.req.routeIndex ? '<- respond from here' : ''`, and the identical example is repeated in the public `hono/route` helper at `src/helper/route/index.ts:26`. `git log -S routeIndex --oneline -- src` surfaces commit `68011665` ("docs: Add JSDoc (#1916)", Kengo Watanabe) as the commit that added this documentation - confirmed by `git show -s` and by reading both cited lines directly. `routeIndex` is therefore a documented, user-facing read surface, not an undocumented internal field as the original research characterized it.

**Correction (independent review, re-verified directly)**: `HonoRequest`'s `GET_MATCH_RESULT` symbol-getter, cited as a precedent K1 could follow, is not analogous on the three axes that matter. Re-checked directly: it exposes a **private** field (`#matchResult`), it is **getter-only** with no setter (`src/request.ts:394`, confirmed by reading the full class - no `set [GET_MATCH_RESULT]` exists anywhere), and it is consumed by **exactly one internal file** (`src/helper/route/index.ts:34`, via an explicit `@ts-expect-error`); `./request/constants` is also absent from `package.json`'s `exports` map, confirmed directly, so the symbol cannot be imported from outside this repository at all. `routeIndex` is the opposite on every axis: public, written as well as read (by both `compose.ts:44` and `src/middleware/combine/index.ts:106`), and documented for user reads per the correction above. A read-only precedent cannot model a field with two writers without inventing a new, unprecedented write-side mechanism.

## History and intentionality (evidence, git archaeology)

**Original verdict (research phase): accidental complexity, with one deliberately-reused piece inside it.** `routeIndex` was introduced in commit `d86fcd41` ("feat(request): Introduce `matchedRoutes` and `routePath` for `HonoRequest` (#1744)", Taku Amano). Three later, unrelated features reused the already-existing public field directly: the `combine` middleware (`#2941`), the `hono/route` helper (`#4204`), and the `method-not-allowed` middleware (`#5132`). Verified: `git show -s` on each cited commit hash confirms author and subject exactly as stated.

**Correction (independent review, re-verified against the actual diff)**: the bug cited as motivating evidence, commit `43497358` ("fix(middleware/combine): prevent `c.req.routeIndex` from being changed (#3663)", Taku Amano), is real, but its mechanism does not point at the remedy K1 proposed. Reading the diff directly (`git show 43497358 -- src/middleware/combine/index.ts`): the offending writer is `compose()` itself, not third-party code reaching into a raw field. The `combine` middleware's `every()` calls `compose()` on a nested middleware array; `src/compose.ts:44` unconditionally assigns `context.req.routeIndex = i` using the *inner* array's indices, overwriting the *outer* chain's value on the same shared `HonoRequest` instance. The fix wraps each inner middleware to restore the saved index: `c.req.routeIndex = currentRouteIndex // should be unchanged in this context`. An accessor whose read/write semantics are, as originally specified, "identical to the existing `routeIndex` field" would be written through by that same nested `compose()` call and would reproduce the identical bug - encapsulating the field's access shape does not address a defect whose actual cause is one piece of per-request state being shared across two logically-independent nested dispatch chains. That underlying defect (nested `compose()` chains sharing one `routeIndex`) is a real, separate finding, but the remedy is scoping or a stack-shaped representation, not an accessor - and is not explored further here, since designing that fix is beyond what this deferred candidate needs to record.

## Migration feasibility (evidence)

**Correction (independent review)**: "an existing abstraction fits" no longer holds as originally stated. A getter/setter pair (the first of the two shapes the original research left open) would not sit *alongside* the existing field - declaring `get`/`set routeIndex()` on the class replaces the own data property with a prototype accessor, contradicting the "purely additive" framing and adding a function-call indirection to the parameter-resolution hot path (`src/request.ts:104,112,114,446`). The symbol-keyed shape (the second option) is genuinely additive, but per the precedent correction above, it has no existing write-side precedent in this repository - it would be new design, not a template being followed. `src/compose.test.ts` never references `routeIndex` and never constructs a `Context` with a `matchResult` (confirmed: `rg -c "new Context\(" src/compose.test.ts` returns 30 constructions, `rg -c "matchResult" src/compose.test.ts` returns 0) - the compose-level test gap identified in the original research is real and independently valuable regardless of K1's fate, since it protects `compose.ts:44`'s assignment itself, including the nested-chain sharing behavior discussed above.

First safe step, retained as valuable on its own: the `compose()`-level characterization test. Adding an accessor on top of it is deferred, not scheduled, pending a re-justified target shape (see "What We Are NOT Doing" in `plan.md`).

Blast radius (unchanged, still verified): `compose.ts` (the writer), `request.ts` (the field's own consumers), and the three external readers/writers - a bounded, fully-enumerated set of 5 files. This axis survives the review's correction; it just no longer carries K1 to the top of the ranking on its own.

# Candidate K2: `Result<T>`'s two-shape union with no discriminant tag

## Current shape (evidence)

`src/router.ts:98`: `export type Result<T> = [[T, ParamIndexMap][], ParamStash] | [[T, Params][]]`. Four router implementations produce one variant or the other with no shared tag: `RegExpRouter`'s matcher returns the 2-tuple `[matcher[1][index], match]` variant (`src/router/reg-exp-router/matcher.ts:28`); `TrieRouter` (`src/router/trie-router/node.ts:215`), `LinearRouter` (`src/router/linear-router/router.ts:149`), and `PatternRouter` (`src/router/pattern-router/router.ts:52`) all return the single-element `[handlers]` variant. `SmartRouter` passes through whichever wrapped router won without normalizing. The sole consumer, `HonoRequest`'s parameter resolution (`src/request.ts:124`), discriminates the two shapes with a plain truthiness check (`this.#matchResult[1] ? ... : ...`) rather than an explicit tag.

## History and intentionality (evidence)

Verdict: **deliberate constraint (performance-driven)**. The union was introduced in commit `ec94acd9` ("feat: one `params` per a handler (optimized for RegExpRouter) (#1566)", Taku Amano and Yusuke Wada), replacing a prior plain object `Result` interface. "Optimized" is literal in the commit title. The change avoids allocating a fresh params object per matched handler on `RegExpRouter`'s hot path by sharing one `ParamStash` array plus per-handler index maps - the two-shape union is a direct consequence of that allocation-avoidance design, not an accident. No commit anywhere discusses rejecting an explicit discriminant tag in favor of the truthiness check specifically - that narrower point is unknown, only the broader allocation rationale is evidenced.

## Migration feasibility (evidence)

Normalizing this union to a single, tagged shape is not something a `request.ts`-only change can achieve - the union is produced at each router's own match/matcher site, so real normalization touches all 4 router implementations plus `router.ts`'s type plus `request.ts`'s consumer, a 6-file change (verified against source, reusing L3's blast-radius framing). A `request.ts`-only shim can only add defensiveness against a shape it doesn't yet see, not eliminate the two-shape reality.

Safeguards found: `src/router/common.case.test.ts`'s shared `runTest()` helper, used by every per-router test file, replicates the same truthiness discrimination as `request.ts` and asserts on resolved params - so a router returning a structurally malformed shape would be caught. It would not catch a router returning a valid-but-wrong member of the union that still happens to resolve params correctly, since nothing pins which variant a specific router is expected to produce. TypeScript's structural typing over the two-tuple union catches malformed shapes at `tsc` time (every PR runs `tsc -p tsconfig.spec.json` before tests, confirmed in `.github/workflows/ci.yml`), but not a "right shape, wrong reason" bug, since there is no discriminant field to check against.

First safe step, if this were pursued: add a router-identity-tagged assertion to `common.case.test.ts` pinning which variant each of the four routers must return, independent of whether params happen to resolve correctly - closing the "right output via the wrong branch" gap before any type change.

# Candidate K3: `#dispatch`'s single-handler fast path duplicates `compose()`

## Current shape (evidence)

`src/hono-base.ts:432-449` is a fast path taken when exactly one handler matched (`matchResult[0].length === 1`, the sole occurrence of this check confirmed with `rg -n "matchResult\[0\]\.length" src`), invoking the handler directly with its own synthetic `next` and its own try/catch routing to `#handleError` (`src/hono-base.ts:401-406`). The composed path (`src/hono-base.ts:452-467`) delegates the same category of work to `compose()` (`src/compose.ts`). Verified structural gap: `compose.ts:33-35` has an explicit "next() called multiple times" guard (`if (i <= index) { throw ... }`, confirmed as the only occurrence of this shape anywhere in `src/` via `ast-grep run --pattern 'if ($I <= $INDEX) { throw $ERR }' --lang ts src`); the fast path's synthetic `next` (`src/hono-base.ts:435-437`) has no equivalent guard, confirmed absent by `rg -n "called multiple times|i <= index" src/hono-base.ts` returning nothing.

## History and intentionality (evidence)

Verdict: **deliberate constraint (performance), with one unaddressed correctness gap inside it**. The fast path was introduced in commit `bb9a9547` ("perf: do not `compose` if it has only one handler (#493)", Yusuke Wada) - `perf:` is the literal commit type, not inferred, and the change explicitly skips `compose()`'s overhead for the common single-handler case. This matches the performance-tuning pattern already documented for this author in `context/map/artifact-3-contributors.md`. Separately, the "next() called multiple times" guard already existed in `compose()` (traceable to a much earlier commit, "Migrate to TypeScript (#21)") before the fast path was added, and no commit at any point retrofits an equivalent guard into the fast path's synthetic `next` - this specific gap looks like an oversight, not a considered trade-off, sitting inside an otherwise clearly deliberate optimization. Corroborating the duplication's ongoing cost: this exact block was independently touched again for correctness at least three more times after its introduction (`#2080`, `#2220`, `#2909`, each re-aligning the fast path's not-found/response behavior with what `compose()` already does elsewhere).

## Migration feasibility (evidence)

This repository has a CI-wired benchmark that specifically isolates single-handler dispatch: `benchmarks/http-server/benchmark.ts` (driven by the PR-gated `http-benchmark-on-pr` job in `.github/workflows/ci.yml`, which posts results as a PR comment on every pull request) defines its primary benchmark route (`app.get('/', ...)`) with no other middleware registered, so it exercises exactly the fast path on every run. A second, non-CI-wired benchmark (`benchmarks/fetch/bench.mts`) explicitly separates a single-handler case from a composed-middleware case, itself evidence the maintainers consider the distinction performance-relevant, not incidental.

This means **merging the two paths** (removing the fast path entirely in favor of always calling `compose()`) is a live, PR-visible risk to a metric this project actively benchmarks and is not a safe default recommendation - it would need a measured before/after run, and even then trades a real, demonstrated optimization for reduced duplication, which is a value call for a maintainer, not something resolvable from evidence alone. **Adding the missing "next() called multiple times" guard to the fast path's synthetic `next`**, by contrast, does not touch the perf-sensitive part of the code at all - it adds one small check to a callback that should never legitimately be called twice, closing a real, verified correctness gap with no expected performance cost and no expected interaction with the benchmark. Existing app-level tests (`src/hono.test.ts`, the sync-throw/async-rejection/no-response-returned/not-found describe blocks already cited in the L3 research) exercise the fast path's other behaviors and would not be affected by adding this guard.

# Candidate K4: duplicated `set-cookie` header-merge logic

## Current shape (evidence) - corrects an L3 finding

L3's research.md described this as "two independent implementations of the same rule" that "currently agree." Direct re-reading of both sites at the pinned commit shows they do **not** agree, in a load-bearing way - this correction is made here, in the L4 exploration, since L3's own scope did not include cross-checking the two implementations' actual runtime behavior against each other, only their existence.

`Context`'s `res` setter (`src/context.ts:414-434`) runs when both an old `this.#res` and a newly-assigned `_res` exist: it iterates the **old** response's headers onto the **new** one, skipping `content-type` (so the new response's content-type always wins), and for `set-cookie` it takes the **old** response's cookies, deletes whatever cookies are already on the new response, and appends the old ones - meaning **the old cookies win and any new cookies set directly on the reassigned response are discarded**. This is confirmed intentional, not a misreading, by `src/context.test.ts`'s own test ("Should set cookie headers when re-assigning Response to `c.res`"): after two cookies are set, then `c.res` is reassigned to a response carrying one different new cookie, the test asserts the result equals the original two cookies, with the new one gone.

`#newResponse` (`src/context.ts:608-654`, backing `c.body()`/`c.json()`/etc.) does the reverse: it seeds header state from the old response, then layers new headers on top, and for `set-cookie` specifically it **appends** rather than replaces - so old and new cookies both survive. Confirmed by `src/context.test.ts`'s "Should keep previous cookies in response headers" test.

So the `content-type` handling produces the same effective outcome in both places (new always wins) via structurally different code, while the `set-cookie` handling is **semantically opposite** between the two call sites: "old wins" on whole-response reassignment vs. "both survive" on incremental body construction.

## History and intentionality (evidence)

Verdict: **accidental complexity**. The `res` setter's rule was introduced in commit `1722144302` ("fix(context): set multiple cookies correctly in `set res` (#1947)", Yusuke Wada). The equivalent rule for what became `#newResponse` was fixed separately, over three months later, by a different, non-maintainer author in `0d06c44b` ("fix(context): keep response cookies in newResponse instead of overwriting (#2555)", Wendell Misiedjan) - neither commit message references the other. That second fix needed its own correction three days later (`253a81de`, Yusuke Wada), and a third, independent instance of the identical class of bug was fixed in a third response-construction path in `ee9ccf8d` ("fix(context): Retain all cookies when passing `ResponseInit` to `c.body` (#2690)", Jari Aarniala) - again with no cross-reference to the prior two fixes. A later consolidation refactor, `9cdfdf3c` ("fix: reduce Context code (#4100)", Yusuke Wada), merged two of these three duplicate blocks into what is now `#newResponse`, but did not touch or merge the `res` setter's separately-duplicated copy, which survives unmerged to the pinned commit. No commit anywhere acknowledges the specific duplication between the setter and `#newResponse`, or the semantic difference between them.

## Migration feasibility (evidence)

Because the two implementations are not behaviorally identical, a naive extraction into one shared helper would be unsafe - it would have to pick one merge direction and silently change the other call site's behavior. `src/context.test.ts` already has direct, named tests for both behaviors (the reassignment test and the "keep previous cookies" test cited above), so a naive consolidation attempt would very likely be caught, but this candidate needs a more careful target shape than originally assumed: a shared helper parameterized over the two differing cookie-merge directions (something like a `mergeResponseHeaders(existing, incoming, { cookieMode: 'replace' | 'append' })` shape), not a single unparameterized merge function.

First safe step: write down (or add as explicit characterization tests) the two merge directions as current, intended behavior, before designing the parameterized helper - this makes the asymmetry a documented contract rather than an implicit fact only visible by reading both code paths side by side.

# Refactor opportunities (ranked)

**Re-ranked after independent plan review** (`reviews/plan-review.md`, finding F7). K1 originally headed this list; the review's counter-question showed three of its four supporting claims were contradicted by the clone (see K1's section above for the corrected evidence). The selected first safe change is now the characterization test plus the fast-path guard, in that order; K1's production-code step (the accessor) moves to deferred, and K4 keeps its original rank.

1. **Selected - `compose()`-level `routeIndex` characterization test.** Current shape: `src/compose.ts:44`'s `context.req.routeIndex = i` assignment, the mechanism a documented public read-surface (`src/request.ts:419`) depends on, has zero test coverage through a real multi-handler dispatch chain (`rg -c "new Context\(" src/compose.test.ts` = 30, `rg -c "matchResult" src/compose.test.ts` = 0). This gap is real and independent of K1's fate - it protects `compose.ts:44` itself, including the nested-chain-sharing behavior the review surfaced as the actual cause of bug `#3663`. Why it is selected: cheapest possible step (test-only, zero production risk), closes a verified gap, and does not depend on resolving K1's deferred re-justification. First step: the test itself.

2. **Selected - Add the missing "next() called multiple times" guard to `#dispatch`'s fast-path synthetic `next`.** Current shape: the fast path's synthetic `next` can be called more than once with no error, unlike `compose()`'s equivalent guard (`src/compose.ts:33-35`). Target shape: a guard matching `compose.ts`'s existing pattern, added to the fast path only - explicitly **not** merging the fast path into `compose()` itself, since that broader merge would trade away a real, CI-benchmarked performance optimization for a duplication cleanup, which is a value judgment beyond this analysis's scope. **Cost correction from review (F3)**: unlike `compose()`, which already tracks dispatch state via `index` (`src/compose.ts:21`), the fast path has no equivalent state today - adding the guard means introducing a new per-dispatch closure flag and assigning it on every legitimate `next()` call, inside the exact route the PR-gated HTTP benchmark measures. The expected cost is small but must be verified, not assumed; see `plan.md`'s corrected Performance Considerations and manual verification step (F4's corrected benchmark invocation). First step: add the guard and closure flag plus a test asserting the fast path's `next` throws on a second call, mirroring `compose.test.ts`'s existing "next() called multiple times" test.

3. **Deferred - K1: encapsulate `routeIndex` behind an accessor.** Deferred, not dropped: the field's small, fully-enumerated blast radius (5 files) still holds, but the original "accidental complexity + existing precedent fits + the historical bug supports this fix" rationale does not (see K1's corrected section above). Before this is re-attempted, the target shape needs re-justifying on the two axes that survive alone, or the candidate needs re-scoping around the defect the review actually found (nested `compose()` chains sharing one `routeIndex` on a single `HonoRequest` instance) rather than around field visibility. Not selected as this plan's production-code deliverable; recorded in `plan.md`'s "What We Are NOT Doing" with the blocker stated (removing or changing a documented public property is a breaking change requiring a deprecation path and a migrated consumer first, neither of which this plan attempts).

4. **K4 - Extract a shared, mode-parameterized header-merge helper for `set-cookie`.** Unchanged by the review. Current shape: two independently-invented, behaviorally-opposite implementations of "how to merge set-cookie headers," discovered during this exploration to not actually agree (correcting the L3 report). Target shape: one helper function taking a merge-direction parameter, called from both the `res` setter and `#newResponse`. Why it is not selected: the fix is more delicate than "delete a duplicate" - it requires first documenting the asymmetry as an intentional contract (via characterization tests) before extracting, since a naive merge would silently change one call site's behavior. Blast radius: `src/context.ts` only, well-covered already by `src/context.test.ts`. First step: add characterization tests pinning both current cookie-merge directions explicitly, before any extraction.

## Considered and rejected

- **K2 - `Result<T>` union normalization.** Rejected for this round: git archaeology shows this is a deliberate, explicitly-labeled ("optimized for RegExpRouter") performance decision, not accidental complexity, and normalizing it touches all four router implementations' hot paths for a benefit that is mostly type-safety rather than a demonstrated bug. If a cheap step is wanted here at all, it would be adding a router-identity-tagged test to `common.case.test.ts` (a test-only change, not a structural refactor, so it does not itself become a ranked candidate) rather than touching the union's shape.

The narrower "add the missing guard" fix (selected above) captures the real, verified correctness gap without touching the benchmarked part.
- **K1's accessor, as a production-code step in this plan.** Deferred per finding F7 above, not implemented in this round.
