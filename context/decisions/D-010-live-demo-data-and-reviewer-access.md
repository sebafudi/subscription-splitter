# D-010: Demo data on the live deployment, and which account a reviewer is given

- **Decision:** The demo plan on the deployed instance is created through the running product by the owner account, in a browser, as part of the release walkthrough - not by a seeding path and not by direct SQL. The gated seed route stays closed: it creates accounts and nothing else, and both accounts it created already exist remotely and survive the four additive migrations, so there is nothing it could contribute. The walkthrough creates one subscription with a start month several months behind the current one, adds the owner and two participants with inclusive membership ranges, records a price and then a price change, marks one break month, records payments including an edit and a delete, and records one standing order with one month marked not received. The throwaway "Deploy smoke test" subscription left on the owner account by the first deployment is renamed rather than removed, because `start_month` is not patchable and the product exposes no `DELETE /api/subscriptions/:id`; renaming is the only housekeeping the domain rules allow. `reviewer@example.com` is deliberately left holding nothing: an empty second account is the ownership-isolation demonstration, not an oversight. A course reviewer who needs to see data is therefore given the owner account's credentials, and the reviewer account is named in the submission comment as the second account proving isolation. Credentials reach the reviewer only through the authorized private channel and are never written into a committed file, a screenshot or a form field that is not the form's own credential field.
- **Rationale:** The release has to show a populated product and prove that another account sees none of it, and those two needs pull in opposite directions for a single account. Creating the data through the product settles both at once and costs nothing extra, because the acceptance walkthrough B08 asks for passes through exactly those screens and the screenshots B12 requires are taken from them. It also makes the demo data honest: every row was produced by a route that validated it, under the ownership rule, exactly as an organizer's data would be. A reviewer opening the owner account lands on a plan with history behind it; a reviewer opening the second account sees an empty list and can be told why.
- **Rejected alternative:** Extending the seed route to write subscriptions, members, prices and payments was rejected because it widens a security-sensitive gated surface, on a live deployment, for a need that arises once - and because it would put rows in the database by a path no ordinary use of the product exercises, which is the opposite of what a certification walkthrough is meant to demonstrate. Writing the rows with `wrangler d1 execute --remote` was rejected for the same reason and a worse one: it bypasses the Zod validation and the ownership joins entirely, so a typo produces a row the application's own invariants would have refused. Seeding a third, pre-populated reviewer account was rejected as disproportionate: it requires reopening the seed route on the live Worker, and it buys only the cosmetic benefit of the reviewer not using the owner's login.
- **Review objection:** Handing a reviewer the owner account lets them edit or delete the demo data, so the screenshots and the live instance can disagree by the time anyone else looks. A second objection is that data created by hand through a browser is not reproducible: nobody can recreate the same demo state later without repeating the clicks.
- **Resolution:** Both are accepted as costs rather than answered away. The screenshots are the record of what the release looked like, are captured before any credential is shared, and carry the release version id alongside them; the live instance is allowed to drift afterwards, because a reviewer exercising CRUD is the product working. Reproducibility is bought back cheaply by writing the exact walkthrough steps and their input values into the release transcript, so the same state can be recreated by following it - the same way `evidence/runs/deploy-1-live-smoke.txt` makes the first deployment's live checks repeatable. Both files use synthetic names and amounts only.
- **Affected tests:** None new. The behaviour this decision relies on is already covered: payment CRUD and its ownership cases in `tests/integration/payments.test.ts`, the patch refusal of `start_month` in `src/server/validation/subscriptions.test.ts`, and the cross-account 404s across `tests/integration/`. The live pass repeats a subset of those against the deployment rather than adding coverage.
- **Commit:** recorded with the `verification-and-release` plan; the live steps it governs land with that change's deploy and verification phase.
