# D-010: Demo data on the live deployment, and which account a reviewer is given

- **Decision:** The demo plan on the deployed instance is a new subscription created through the running product by the owner account - not by a seeding path and not by direct SQL. The gated seed route stays closed: it creates accounts and nothing else, and both accounts it created already exist remotely and survive the four additive migrations, so there is nothing it could contribute. The pre-existing "Deploy smoke test" subscription is not used as the demo plan and not used as the live transcript's parent: its start month is the month of the first deployment, so it has no elapsed history to show, and it carries no `members` row at all, because it was created before `0003_members.sql` was applied remotely. No share and no balance can be computed against a subscription with no owner member (decision D-006), so any figure read from it would be meaningless.

  The live pass is therefore planned in two halves against one new subscription. The API transcript creates it - which also creates its owner member and that member's opening range in one batch - then its two participants, its price and price change, and its break month, and runs the payment create, read, update and delete cycle against a third participant added for that purpose and deleted again before the phase closes. The browser walkthrough then records the money a reviewer actually looks at: two payments, an edit, a standing order and one month marked not received.

  Everything the live pass creates is permanent unless the product itself can delete it. Payments, prices, break months, schedules, exceptions and non-owner participants all have delete routes. Subscriptions do not, and the owner member answers 409 to a delete before the dependents check is even reached. So exactly one subscription and one owner member are created on purpose and kept; anything created only to demonstrate a verb hangs off a non-owner participant and is removed with that verb.

  The "Deploy smoke test" subscription is repaired and relabelled rather than removed. It gets an owner member through `POST /api/subscriptions/:id/members` with an active range opening at its own start month, which turns a state the shipped product can no longer produce into an ordinary empty plan; that owner member is permanent, which is accepted because the row it sits on is permanent anyway. If the range is refused it stays owner-less and that is recorded rather than worked around. Either way it is renamed through `PATCH /api/subscriptions/:id` to a label that tells a reviewer it is the first deployment's artefact and not the demo plan, and the release summary says why it cannot be removed.

  `reviewer@example.com` is deliberately left holding nothing: an empty second account is the ownership-isolation demonstration, not an oversight. A course reviewer who needs to see data is therefore given the owner account's credentials, and the reviewer account is named in the submission comment as the second account proving isolation. Credentials reach the reviewer only through the authorized private channel and are never written into a committed file, a screenshot or a form field that is not the form's own credential field.
- **Rationale:** The release has to show a populated product and prove that another account sees none of it, and those two needs pull in opposite directions for a single account. Creating the data through the product settles both at once and costs nothing extra, because the acceptance walkthrough B08 asks for passes through exactly those screens and the screenshots B12 requires are taken from them. It also makes the demo data honest: every row was produced by a route that validated it, under the ownership rule, exactly as an organizer's data would be. A reviewer opening the owner account lands on a plan with history behind it; a reviewer opening the second account sees an empty list and can be told why. Splitting the creation across the transcript and the browser, rather than doing it all in one or the other, is what lets both halves of the evidence describe the same rows: the transcript can name the subscription and member every request acts on, and the screenshots show the plan that transcript built.
- **Rejected alternative:** Running the live transcript against the existing "Deploy smoke test" subscription, repairing it and using it as the demo plan, was rejected on the facts: its start month cannot be moved, so it can never show an elapsed standing order, a price change over time or a departed participant, which are the behaviours the release exists to demonstrate. Repairing it is still worth doing, but as housekeeping rather than as the demo. Extending the seed route to write subscriptions, members, prices and payments was rejected because it widens a security-sensitive gated surface, on a live deployment, for a need that arises once - and because it would put rows in the database by a path no ordinary use of the product exercises, which is the opposite of what a certification walkthrough is meant to demonstrate. Writing the rows with `wrangler d1 execute --remote` was rejected for the same reason and a worse one: it bypasses the Zod validation and the ownership joins entirely, so a typo produces a row the application's own invariants would have refused. Seeding a third, pre-populated reviewer account was rejected as disproportionate: it requires reopening the seed route on the live Worker, and it buys only the cosmetic benefit of the reviewer not using the owner's login.
- **Review objection:** Handing a reviewer the owner account lets them edit or delete the demo data, so the screenshots and the live instance can disagree by the time anyone else looks. A second objection is that data created by hand through a browser is not reproducible: nobody can recreate the same demo state later without repeating the clicks. An independent plan review raised a third, which is why this decision was rewritten: the original text named no parent record for the live transcript at all, and the only subscription that existed when the transcript runs is one that has no owner member and cannot be deleted, so the transcript as written had nothing valid to act on and no account of what its actions would permanently leave behind.
- **Resolution:** Both are accepted as costs rather than answered away. The screenshots are the record of what the release looked like, are captured before any credential is shared, and carry the release version id alongside them; the live instance is allowed to drift afterwards, because a reviewer exercising CRUD is the product working. Reproducibility is bought back cheaply by writing the exact walkthrough steps and their input values into the release transcript, so the same state can be recreated by following it - the same way `evidence/runs/deploy-1-live-smoke.txt` makes the first deployment's live checks repeatable. Both files use synthetic names and amounts only.
- **Affected tests:** None new. The behaviour this decision relies on is already covered: payment CRUD and its ownership cases in `tests/integration/payments.test.ts`, the patch refusal of `start_month` in `src/server/validation/subscriptions.test.ts`, the owner-member delete refusal and the dependents refusal in the members tests, and the cross-account 404s across `tests/integration/`. The live pass repeats a subset of those against the deployment rather than adding coverage.
- **Commit:** recorded with the `verification-and-release` plan; the live steps it governs land with that change's deploy and verification phase.
