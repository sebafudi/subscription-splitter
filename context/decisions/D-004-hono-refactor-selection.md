# D-004: Hono refactor selection

- **Decision:** From the ranked options in `context/changes/hono-refactor-opportunities/research.md`, the selected changes are: (1) a `compose()`-level characterization test proving `HonoRequest.routeIndex` advances correctly across a real multi-handler dispatch chain, and (2) adding the missing "next() called multiple times" guard to `#dispatch`'s single-handler fast-path synthetic `next`. K1 (encapsulating `routeIndex` behind an accessor) was originally selected as the top-ranked candidate but is now deferred, not implemented, following independent plan review - see Review objection and Resolution below. Both selected changes target `honojs/hono` at the pinned commit `edd138ee3049749190de3dcd7e32d7bcbf224e41`; this refactor targets that separate analysis repository, not the subscription-splitter application. Implementation of the resulting plan is optional for this exercise - the required deliverable is the ranked research and the plan itself, not landed code.
- **Rationale:** The characterization test closes a real, verified coverage gap - `compose.ts:44`'s `routeIndex` assignment has zero test coverage through a real multi-handler chain today - and is valuable independent of K1's fate, since it protects the exact mechanism a documented public read surface (`src/request.ts:419`) depends on. The fast-path guard closes a genuinely verified correctness gap (the fast path lacks the "called twice" protection `compose()` already has) at the lowest cost in the candidate set, and does not compete with or depend on the deferred K1 work. Both changes are additive or test-only, have no file overlap with each other, and do not touch the parts of the codebase (the router hot path, the CI-benchmarked fast-path optimization itself) that were verified as deliberate performance decisions not to be disturbed.
- **Rejected alternative:** K4 (extract a shared, mode-parameterized `set-cookie` header-merge helper) remains ranked below the selected pair: the exploration discovered the two existing implementations are not behaviorally identical (old-cookie-wins on reassignment vs. both-survive on incremental body construction), so a naive extraction would be unsafe, and the correct target shape needs the asymmetry documented as an intentional contract before any code is touched - real, valuable work, but a higher first-step cost than either selected change, so it stays deferred. K2 (`Result<T>` union normalization) remains rejected for this round: git archaeology shows it is a deliberate, explicitly-labeled performance decision ("optimized for RegExpRouter"), and normalizing it touches all four router implementations' hot paths for a benefit that is mostly type-safety rather than a demonstrated bug. The broader "merge the fast path into `compose()` entirely" framing remains rejected in favor of the narrower guard-only fix, because a PR-gated HTTP benchmark in this repository's own CI specifically isolates the single-handler dispatch path, meaning removing it is a value trade-off against a measured metric, not a safe default recommendation.
- **Review objection:** Independent plan review (`context/changes/hono-refactor-opportunities/reviews/plan-review.md`) tested K1's top rank with a counter-question and found three of its four supporting claims contradicted by direct evidence in the clone: (1) `routeIndex` was characterized as an undocumented internal field, but it is documented for user-land reads in a public `@example` JSDoc block (`src/request.ts:419`, added deliberately by a commit titled "docs: Add JSDoc"), and the identical example is repeated in a public helper; (2) the cited `GET_MATCH_RESULT` precedent was characterized as a fitting existing abstraction, but it is private, getter-only, and consumed by exactly one internal file, where `routeIndex` is public, read-write, and documented - not analogous on any of the three axes that matter, and its write half would be new, unprecedented design; (3) the historical bug cited as motivation (`#3663`) was characterized as third-party code reaching into a raw field, but reading the actual diff shows the offending writer was `compose()` itself, overwriting shared per-request state across nested dispatch chains - an accessor with identical read/write semantics, as originally specified, would reproduce the same bug rather than prevent it. Only two of the original four supporting claims survive: the blast radius is genuinely small and fully enumerated, and a test-only first step is genuinely additive.
- **Resolution:** K1's production-code step (the accessor) is deferred, not implemented in this plan. The two surviving axes (bounded blast radius, additive first step) were judged not to outweigh the loss of the correctness argument that originally justified ranking K1 above the alternatives - a small, well-understood blast radius is a reason a fix is *safe to attempt*, not a reason it is *worth attempting*, and with the "already caused a bug this fixes" and "existing pattern already fits" claims both refuted, the case for spending review and implementation attention on the accessor specifically no longer holds. The selected replacement is the pairing of (a) the characterization test, which is independently justified regardless of K1's fate and was already going to be Phase 2's prerequisite, and (b) the fast-path guard, which was already selected on its own merits and is unaffected by anything the review found about K1. If K1 is revisited, the review's own finding points at a different, more specific target: the defect `#3663` exposed is that a `HonoRequest`'s `routeIndex` is shared, unscoped state across nested `compose()` dispatch chains, which calls for a scoping or stack-shaped fix, not an access-shape change - that re-scoped candidate is not designed further here and would need its own exploration pass.
- **Affected tests:** In the Hono clone (not this application): a new `compose()`-level characterization test exercising `routeIndex` advancement through a real multi-handler chain; a new test asserting the fast path's synthetic `next` throws on a second call, mirroring `src/compose.test.ts`'s existing "next() called multiple times" test. No tests in this repository are affected.
