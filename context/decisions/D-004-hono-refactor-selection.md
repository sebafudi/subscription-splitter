# D-004: Hono refactor selection

- **Decision:** From the ranked options in `context/changes/hono-refactor-opportunities/research.md`, the selected first safe change is the top-ranked candidate, K1: encapsulate `HonoRequest.routeIndex` behind an accessor, following the existing `GET_MATCH_RESULT` symbol-getter precedent already shipped in the same class. A cheap quick win flagged by the ranking is bundled alongside it: the narrowed K3 fix, adding the missing "next() called multiple times" guard to `#dispatch`'s single-handler fast-path synthetic `next`. Both target `honojs/hono` at the pinned commit `edd138ee3049749190de3dcd7e32d7bcbf224e41`; this refactor targets that separate analysis repository, not the subscription-splitter application. Implementation of the resulting plan is optional for this exercise - the required deliverable is the ranked research and the plan itself, not landed code.
- **Rationale:** K1 is the strongest candidate on every axis the ranking evaluated: its history verdict is accidental complexity (not a deliberate trade-off to respect), it already caused one real, fixed bug (`#3663`, a nested `compose()` call stomping on the outer `routeIndex`), an existing in-repo abstraction (`GET_MATCH_RESULT`) already fits the target shape, its blast radius is small and fully enumerated (5 files), and its first step is purely additive and non-breaking. The K3 quick win is bundled because it is the cheapest possible fix in the entire candidate set (a one-line guard plus a mirroring test), closes a genuinely verified correctness gap, and has zero interaction with the part of K3 that git archaeology showed to be a deliberate, CI-benchmarked performance optimization - it does not compete with K1 for review attention or touch overlapping files.
- **Rejected alternative:** K4 (extract a shared, mode-parameterized `set-cookie` header-merge helper) was ranked third, not selected first, because the exploration discovered the two existing implementations are not behaviorally identical (old-cookie-wins on reassignment vs. both-survive on incremental body construction) - a naive extraction would be unsafe, and the correct target shape needs the asymmetry documented as an intentional contract before any code is touched. This is real, valuable work but has a higher first-step cost (characterization tests for two divergent behaviors, not one) than K1, so it is deferred rather than selected as the first change. K2 (`Result<T>` union normalization) was rejected entirely for this round: git archaeology shows it is a deliberate, explicitly-labeled performance decision ("optimized for RegExpRouter"), and normalizing it touches all four router implementations' hot paths for a benefit that is mostly type-safety rather than a demonstrated bug - not a good first candidate to disturb. The broader "merge K3's fast path into `compose()` entirely" framing was also rejected in favor of the narrower guard-only fix, because a PR-gated HTTP benchmark in this repository's own CI specifically isolates the single-handler dispatch path, meaning removing it is a value trade-off against a measured metric, not a safe default recommendation.
