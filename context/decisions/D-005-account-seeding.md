# D-005: Account seeding

- **Decision:** The owner and reviewer accounts are created through a gated, idempotent seed route, `POST /api/dev/seed`, which is mounted only when the environment variable `SEED_ENABLED` equals `"true"` and which additionally requires the header `x-seed-token` to equal the secret `SEED_TOKEN`. When either gate fails the route answers 404, so its existence is not detectable. The accounts to create are supplied in the request body as email, password and name; no credential ever appears in source, in a fixture or in a committed file. Creation goes through a second Better Auth instance constructed against the same D1 binding with `emailAndPassword.disableSignUp: false`, while the application's own instance keeps sign-up disabled, which is the pattern the compatibility spike verified. Calling the route twice is safe: an email that already exists is reported as unchanged rather than failing. Local values live in `.dev.vars`, which is ignored by git; `.dev.vars.example` lists the variable names only. The remote procedure, to be followed once under slice S-04, is to set `SEED_ENABLED` and `SEED_TOKEN` on the deployed Worker, call the route once with the real credentials, then remove both variables so the route stops existing.
- **Rationale:** Better Auth's public sign-up endpoint is disabled by product decision, so some server-side path has to create the two accounts. The alternatives all fail on either safety or reproducibility: a one-off local script cannot reach D1, which is only addressable from inside a Worker; a manual SQL insert would have to reproduce the library's password hashing by hand and would drift the moment the library changes it. A route that uses the library's own `signUpEmail` is the only path that produces exactly the rows the library expects, and gating it behind a flag plus a secret, with a 404 rather than a 401 on failure, keeps it from being an account-creation hole in any environment where the variables are not set.
- **Rejected alternative:** A permanent unauthenticated seed route, as used in the spike, was rejected because it is an open account-creation endpoint in every environment it ships to. Seeding from credentials checked into source or into a migration was rejected because it commits passwords and makes rotating them a code change. A separate administrative interface was rejected as disproportionate for two accounts that are created once.
- **Review objection:** Any seeding path is an account-creation hole, and a route that is only disabled by configuration can be enabled by a configuration mistake. A second objection is that 404 on a failed token check hides genuine misconfiguration from whoever is running the seed.
- **Resolution:** The double gate means a single mistaken variable is not enough: the flag mounts the route and the secret authorises the call. The 404 is deliberate, since a 401 would confirm the route exists to anyone probing for it; the operator running the seed has the logs and the variables in front of them, so the ambiguity costs them little. The remote procedure ends by removing both variables, so the enabled window is bounded by one deployment step. An integration test asserts the route is absent when the flag is off.
- **Affected tests:** Integration tests added in the runtime-auth slice: a seed call with the gate off returns 404; a seed call with the gate on but a wrong token returns 404; a seed call with the gate on and the right token creates the accounts and a second identical call reports them unchanged; the public sign-up endpoint stays refused throughout.
- **Commit:** recorded when the runtime-auth slice lands.
