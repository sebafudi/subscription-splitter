# 01: Domain distillation

## Step 0: Project context discovered

This is a library/framework, not an application with a PRD - there is no `prd.md`, `tech-stack.md`, or `foundation/` directory in this clone. The vision/requirements material used as the "context document" is: the repository's own `README.md` (85 lines), `package.json`'s `description` and `keywords` fields, and `jsr.json`'s `exports` map (76 public entry points). No extended narrative or design-decision document exists beyond these; this absence is itself a limitation, noted below rather than filled in with invented vision text.

Stack and structure: TypeScript, single package (no workspaces), business logic lives in `src/` across `hono.ts`/`hono-base.ts` (the app), `context.ts`/`request.ts` (the request/response object model), `compose.ts` (middleware execution), `router.ts` plus `router/*` (route matching, 5 implementations), `middleware/*` and `helper/*` (cross-cutting features), and `adapter/*` (per-runtime glue). There is no separate "service" or "persistence" layer - this is a request-dispatch library, not a data-owning application.

## Step 2: Subdomain classification

| Concept | Category | Justification |
|---|---|---|
| Router (route matching) | **Core** | Named explicitly as the product's headline differentiator ("Ultrafast... RegExpRouter is really fast. Not using linear loops"); this is the one place the README makes a competitive, technical claim rather than a generic feature claim |
| Context / request-response model | **Core** | Every code example and the entire public API surface (76 `jsr.json` exports) is built around handlers receiving a `Context`; this is the object every other concept (middleware, router, adapters) exists to serve |
| Middleware composition (`compose.ts`) | **Core** | "Batteries Included" is one of five headline features; the composition mechanism is what makes middleware "composable" at all, not an implementation detail |
| Adapters (multi-runtime) | **Core** | "Multi-runtime - the same code runs on all platforms" is a headline feature, not a convenience; it is the product's central promise that a Hono app is portable |
| Web Standards commitment (`Request`/`Response` as the domain type) | **Core** | The architectural decision that makes "the same code runs on all platforms" possible at all (see `03-anti-corruption-layer.md`) |
| Built-in middleware (cors, jwt, compress, etc.) | **Supporting** | Valuable, and part of "Batteries Included," but each is independently replaceable/optional and does not define what Hono fundamentally is |
| Presets (`tiny`, `quick`) | **Supporting** | Packaging/configuration convenience over the core, not a distinct capability |
| RPC client (`hc`) | **Supporting** (with a documentation gap, see Step 4) | A real, actively-maintained capability, but one an app can fully ignore and still be "Hono" - the README's five headline features do not mention it |
| JSX runtime (`src/jsx/*`) | **Supporting** | A substantial subsystem (highly active per `artifact-1-territory.md`) but orthogonal to routing/dispatch - an app can use Hono with zero JSX |
| Validator | **Supporting** | Valuable, schema-library-agnostic by design (see `03-anti-corruption-layer.md`), but not what makes Hono "Hono" |
| Utils (`src/utils/*`: cookie, jwt primitives, url, mime, etc.) | **Generic** | Reusable, domain-agnostic building blocks any HTTP framework needs; none are Hono-specific concepts |

## Step 3: Aggregate candidates and their invariants

| Candidate aggregate | Invariant (must always be true) | Source citation | Enforcement status |
|---|---|---|---|
| `Context` (owns request/response state for one dispatch) | Once a response is finalized, subsequent handler code should not silently corrupt previously-set response state (e.g. drop cookies) when the response is replaced or extended | Implied by "Web Standards" (`README.md:22`) - a standards-compliant HTTP layer must not silently drop `Set-Cookie` headers a caller already set | **Declared but inconsistently enforced** - see `02-invariant-aggregate-refactor.md`; `Context`'s `res` setter and its `#newResponse` helper implement opposite policies for this exact case |
| `HonoRequest` (owns per-dispatch routing state) | The parameter data returned by `.param()` must always correspond to the currently-executing step of a multi-handler dispatch chain | Implied by the router being a headline feature (`README.md:41`) - parameter resolution correctness is inseparable from routing correctness | **Declared, weakly verified** - `routeIndex` (`src/request.ts:53`) carries this invariant but has zero test coverage of it through a real `compose()`-driven chain (confirmed in `context/changes/hono-request-dispatch-analysis/research.md` and `context/changes/hono-refactor-opportunities/research.md`) |
| `Router<T>` implementations (route matching) | All implementations must produce a `Result<T>` shape that every consumer can interpret identically, regardless of which of the 5 implementations is active (relevant given `SmartRouter` can switch between two at runtime) | Implied by "the same code runs on all platforms" extended to "the same code runs with any router" (`README.md:56`: `router` is a swappable `HonoOptions` field) | **Enforced structurally but not semantically tagged** - a two-shape untagged union (`src/router.ts:98`), each router agreeing informally on which shape it returns; see `context/changes/hono-refactor-opportunities/research.md`'s K2 |

## Step 5: Refactor ranking

Ranking aggregate candidates from Step 3 by value (how core the invariant is) times risk (how weakly it is enforced today):

1. **`Context`'s response/cookie-merge invariant** - highest combined score: core to a "Web Standards" HTTP library's basic correctness, and the only one of the three candidates with a **proven, live inconsistency** (not just a coverage gap) between two code paths that both claim to implement it. Selected as invariant #1 for `02-invariant-aggregate-refactor.md`.
2. **`HonoRequest`'s `routeIndex`/parameter-resolution invariant** - core to routing correctness, weakly verified (no compose-level test), and already the direct subject of `context/changes/hono-refactor-opportunities/research.md`'s selected K1 candidate (structural encapsulation) - the domain lens here reinforces, rather than replaces, that code-structure-driven finding.
3. **`Router<T>`'s cross-implementation shape agreement** - core to the "swap the router" feature, but verified as a deliberate performance-driven design (`context/changes/hono-refactor-opportunities/research.md`'s K2), and its type-level enforcement, while not semantically tagged, has not been shown to fail in practice - lowest urgency of the three.

## Summary

This distillation is built from Hono's own `README.md`, `package.json`, and `jsr.json`, since no PRD or extended vision document exists for this framework repository - that absence is a real limitation of the source material, not filled in with invented context. The ubiquitous language centers on `Hono`/`Context`/`Handler`/`Middleware`/`Router`/runtime `Adapter`, with the "built on Web Standards" commitment as the architectural idea that ties the multi-runtime promise together. Two concepts are absent from the README despite being substantial in code: the RPC client (`hc`) and the word "Context" itself, which the README's examples rely on without ever naming. The most consequential model-vs-code gap is that this repository's own adapters do not cover two of the eight runtimes the README lists (Node.js, Fastly Compute), because those are served by a separate package or need no adapter at all - worth a reader's attention before assuming "supports X" always means "ships an adapter for X" in `src/`. The strongest refactor candidate to emerge from a domain lens is `Context`'s response-cookie-merge invariant, which is not just weakly tested but actively implemented two different, contradictory ways today - carried forward into `02-invariant-aggregate-refactor.md`.
