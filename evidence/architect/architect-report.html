3. Feature analysis (L3)

Source: context/changes/hono-request-dispatch-analysis/research.md. Studied flow: request dispatch (Hono.fetch into #dispatch, router match, compose(), Context, Response), chosen because the map's risk zones and first-day list both point at this exact core. Feature overview: a request enters through fetch(), the path is matched against registered routes, a single matched handler runs directly while multiple handlers run through compose(), which advances a per-step route index as it walks the chain, and the resulting Context produces the final Response. Technical debt, at least one item ast-grep confirmed: compose()'s per-step route-index advancement has no test through a real multi-handler chain (confirmed: zero matchResult references in compose.test.ts against 30 Context constructions); the response's cookie-header-merge logic is implemented twice with opposite behavior, a correction made in L4 and independently in L5, not in agreement as this artifact first assumed; the fast dispatch path lacks a safety guard the general dispatch path already has (confirmed as the guard's only occurrence in src/).

4. Refactor plan (L4)

Source: context/changes/hono-refactor-opportunities/{research.md,plan.md}, context/decisions/D-004-hono-refactor-selection.md. Originally selected: encapsulating a raw, public routing-state field behind an accessor. An independent plan review tested that choice with a counter-question and refuted three of its four supporting claims directly against the code (the field is documented for user reads, the cited precedent does not match its shape, and the historical bug it was meant to fix was actually caused elsewhere). The plan was re-ranked: that accessor is now deferred, and the selected changes are two phases. Phase 1, the characterization test: verified automatically by typecheck, test, lint and format, and manually by reading the test to confirm it dispatches through the real composer rather than setting the index by hand. Phase 2, the fast-path guard: the same four automated checks plus build and a bundle-size check, and manually by running the project's HTTP benchmark against the pinned commit as baseline. Explicitly not doing: the deferred accessor, which is blocked because it would be a breaking change to a documented public property; normalizing the router's matching-result shape, a verified deliberate performance decision; or consolidating the cookie-merge duplication, which needs its own characterization step first, since the two implementations were found to disagree, not just duplicate.

5. Domain notes (L5)

Source: context/domain/01-domain-distillation.md, 02-invariant-aggregate-refactor.md, 03-anti-corruption-layer.md. Ubiquitous language: Hono, Context, Handler, Middleware, Router, runtime Adapter, and the "built on Web Standards" commitment; the sharpest model-vs-code gap is that the project's own README lists two runtimes (Node.js, Fastly Compute) that this repository's own adapters do not actually ship. Invariant #1, on the Context aggregate: response cookies must be preserved when headers are merged. It is found not merely weakly tested but actively violated today, since the response's two header-merge code paths implement opposite cookie policies (one drops new cookies on reassignment, the other keeps both), independently corroborating the L4 finding. Anti-corruption layer: checked the AWS Lambda, Lambda@Edge, and Cloudflare Pages adapter boundaries plus the validation-library boundary; grep/ast-grep scoped outside each adapter directory found zero cross-boundary imports in every case, a genuine absent-leak result.

6. Decisions that belong to me

Choosing Hono, rather than the Builder application, as the module 4 analysis target was my call: the Builder app is a fresh build with no real commit history to mine, so analyzing it would have meant inventing contributor and co-change evidence that does not exist. Within Hono, I chose the request-dispatch flow specifically because two independent artifacts (map risk zones, first-day reading list) converged on it, not because it looked interesting. When the independent plan review refuted the top-ranked refactor candidate's supporting claims, I deferred that candidate rather than defending or patching the original justification; the corrected evidence changed what was actually worth doing, so the plan changed with it. Once the cookie-merge duplication turned out to be a behavioral disagreement rather than harmless repetition, I chose to defer consolidating it behind a characterization step rather than proposing a quick merge that could silently change one code path's behavior. For the anti-corruption-layer check, I chose to recommend a preventive CI check rather than any remediation, because the boundary was already clean; recommending a fix for a problem that does not exist would have been the wrong call.
