=============== 8. FAILURE: the callback never reaches the Worker in a browser ===============
This is the one live check that failed. It is recorded and not patched, per the task's rule.

Driving the fabricated-state callback as a real top-level browser navigation rather than with curl:

  navigate to /api/auth/callback/google?state=bogus2&code=bogus2
  URL the document actually loaded at: .../api/auth/callback/google?state=bogus2&code=bogus2
  no redirect occurred; the client shell was served at the callback path with the query intact
  rendered alert text: empty      rendered status text: empty
  expected: a 302 to /?error=state_mismatch and the expired-link alert on the login screen

The same request by curl does redirect, so the difference is the request shape, not the code. A
single-variable matrix isolates the trigger exactly. Status, content-type and Location as returned:

  callback, no special headers                 302  application/json  location: /?error=state_mismatch
  callback, Accept: text/html only             302  application/json  location: /?error=state_mismatch
  callback, Sec-Fetch-Dest: document only      302  application/json  location: /?error=state_mismatch
  callback, Accept: */* + Sec-Fetch-Dest: doc  302  application/json  location: /?error=state_mismatch
  callback, Sec-Fetch-Mode: navigate only      200  text/html         (index.html, no Location)

  /api/me,          Accept: text/html          401  application/json
  /api/health,      Accept: text/html          200  application/json
  /api/auth-config, Accept: text/html          200  application/json

The single deciding header is Sec-Fetch-Mode: navigate. Any top-level document navigation to a path
that is not a static asset is answered by Cloudflare's asset layer with index.html at 200 and never
reaches the Worker. wrangler.jsonc sets:

  "assets": { "not_found_handling": "single-page-application" }

and nothing that asks the Worker to run first. That block has been in wrangler.jsonc since the
scaffold (c85b946, then 909dd6a); `git diff --stat c842f64..HEAD -- wrangler.jsonc` is empty, so the
google-sign-in change neither introduced nor altered it.

Why it did not surface before: every earlier API call the client makes is fetch/XHR, which carries
Sec-Fetch-Mode: cors or same-origin and passes through to the Worker untouched. That is why password
sign-in, sign-out, the subscription reads and /api/auth-config all still work in the browser and all
pass above. The OAuth return leg is the first thing this application does that requires a top-level
document navigation to an /api path, and it is exactly the shape the asset layer intercepts.

Consequence: on this deployment a real Google sign-in cannot complete. Google would 302 the browser
to /api/auth/callback/google?code=...&state=..., that navigation would be answered with index.html,
the authorization code would never be exchanged and no session would be created. The user would land
on a bare login screen with no message. The same interception is why the expired-link alert could not
be produced in the browser here.

Not a regression, and no rollback is indicated: nothing that worked before this release works less
well now, and every pre-existing behaviour is verified passing above. It is a deployment
configuration gap that this feature is the first to depend on.
